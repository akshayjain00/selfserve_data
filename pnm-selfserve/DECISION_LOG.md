### D4 — Nano business rule (owner domain knowledge)
- **Date:** 2026-07-08 · **Status:** ACTIVE (baked into SQL)
- **Rule:** Nano = labour-only help (no vehicle/vendor allocated), owned by **LA (Labour Assist)**, a separate business group.

### D21 — Build `leads` city + week cuts (`PNM-G-070` pilot)
- **Date:** 2026-09-22 · **Status:** DONE (implemented) · Branch `pnm_cadenceGap_fix`.
- **Context:** `PNM-G-070` — "the catalog cannot be cut by city or by week" — is one of the KB's largest owner-blocked gaps. Unlike every other section built to date, there is no MBR-automation query to mirror for either cut (the automation is PnM-wide/monthly only), so this needed new SQL validated a different way. Scoped deliberately small: one section (`leads`), both dimensions, not all six sections from the gap's own next_action.
- **Reconciliation approach, ruled in-session:** try a Metabase cross-check first, fall back to self-consistency. Metabase MCP was attempted twice — once mid-session, once after a full Claude Code session reconnect specifically to get it working — and never appeared as a callable tool either time. Ruled final: this pilot ships on **self-consistency only**, explicitly flagged as such in `metrics.md`, not silently upgraded to "reconciled." Follow-up: attempt the cross-check again once Metabase access exists in a session.
- **Boundary-week ruling:** a week that spans two calendar months (confirmed live and real, not a rare edge — most months don't start on a Monday) is answered **in full**, labelled explicitly as spanning two months — same honesty-over-convenience precedent as MTD labeling, rather than refused or clipped.
- **Architecture:** `metrics_registry.py` gained per-section capability flags (`SECTIONS["leads"]["supports_city"]`/`["supports_week"]`, both `True`, every other section implicitly `False`) — the template for extending city/week to more sections later. `UNSUPPORTED_TERMS`' 14 hardcoded city names + `ahmedabad`/`ahemdabad` were pulled out into a new `CITIES` map (conditional on the matched metric's section, not an unconditional block); a new `WEEK_RE` recognizes "week of/starting YYYY-MM-DD" phrasing. Generic breakdown terms (`city-wise`, `weekly trend`, etc.) stayed unconditionally blocked everywhere — this pilot answers one named city or one specific week per question, never a `GROUP BY`/trend. `resolve()`'s return shape changed from `(metric_id, reason)` to `(metric_id, city, week_start, reason)` — every caller (`ask.py`, `run_tests.py`) updated in the same change.

### D27 — Trend support: "weekly/daily trend" answers a real multi-row breakdown instead of refusing (`PNM-G-070` trend close-out)

- **Date:** 2026-09-22 · **Status:** DONE (implemented) · Branch `pnm_cadenceGap_fix`.
- **Context:** `D25` generalized week/day as a NARROWING of the month filter — one row, a smaller window. Owner pushback, explicit and repeated this session: a "weekly/daily trend" question ("weekly orders trend for May 2026", "orders per day") should not refuse at all — take the same monthly query, widen it back out to the whole month, and group it by week/day instead, returning the real trend numbers. This is a different request shape from `D25`'s single-period narrowing (one row vs. many), explicitly out of scope when `D25` shipped (see that entry's own "not part of this ask" framing) — this entry is what closes that gap.
- **The mechanical argument, verified again before writing code:** every section's month filter is `col >= month_start AND col < next_month_start` (or the DATE_TRUNC equality `D25` already uses). A trend needs exactly that same WHERE clause, WIDENED to the whole month instead of one narrower period, with the `SELECT`/`GROUP BY` keyed on `DATE_TRUNC('week'|'day', col)` instead of a literal date. For sections that already emitted a literal `DATE '{row_date}' AS month` with no `GROUP BY` (the majority — `leads`/`orders`/`p80_durations`/`ota`/`allocation`/etc., which aggregate ONE row over their whole WHERE match), this needs an actual `GROUP BY` added — not present in the single-period version. Sections that already grouped internally to join CTEs together (`tpo`, `vendor_tpo_top5`, `wallet`) needed only the WHERE widened and the grain narrowed — the existing `GROUP BY`/join-on-period structure carries a trend naturally.
- **The one case needing more than a filter change:** `vendor_earnings_bucket`'s "latest vendor bucket in the period" (`ROW_NUMBER() OVER (PARTITION BY vendor_id ...)`) and its revenue-% denominator (`SUM(...) OVER ()`) were computed over the WHOLE month in the single-period query. A trend needs both computed PER WEEK/DAY, or every period but the last would silently get wrong percentages (a vendor's month-end bucket applied backwards, revenue-% denominators pooling across periods instead of within one). Fixed by adding `PARTITION BY period` to both window functions — verified live afterward: every week's 5 bucket percentages independently summed to ~100% (99.99–100.01, rounding noise), the exact invariant that breaks first if the partition were missing.
- **What changed:**
  - `sqlgen.py`: new `trend_filter(col, month, grain)` (WHERE-range + grouped `SELECT` expression for the single-CTE case) and reuses `period_grain()` directly where a section's `period` column is used to JOIN CTEs, not just filter. 16 new `*_trend_sql()` functions — one per built section except `fare` (same reason `fare` has no week/day variant, `D25`) — collected in `TREND_SQL` and dispatched via a new `render_trend(section, month, grain, city=None)`, defensive-checked the same way `render()` is.
