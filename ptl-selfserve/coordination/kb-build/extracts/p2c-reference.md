## Architecture pattern being replicated

The PnM engagement locked in a specific shape that the PTL self-serve build inherits wholesale:

1. **Closed-world metric registry.** A declarative catalog (`metrics_registry.py`) is the *only* thing the NL layer may select from — "it never authors SQL." Anything off-menu (new dimension, new grain, uncataloged metric) is refused, never improvised. `repo@851886f:pnm-selfserve/selfserve_nlq/metrics_registry.py#L1-L5`; `repo@851886f:pnm-selfserve/iteration-1-metric-catalog-and-architecture.md#L278` ("closed-world: it can only answer questions that resolve to a catalog metric... never improvised. This mirrors the Argus confidence model").
2. **Deterministic SQL engine, separate from the AI.** `sqlgen.py`/`ask.py` render one parameterized, read-only SELECT per section; an `assert_read_only` guard enforces this. The AI's role is explicitly bounded to mapping natural language → a registry metric id, nothing else — "Snowflake credentials are exercised only through `ask.py`." `repo@851886f:pnm-selfserve/iteration-1-metric-catalog-and-architecture.md#L336-L343`; `repo@851886f:pnm-selfserve/selfserve_nlq/README.md#L7-L20`.
3. **Dry-run by default.** `ask.py` prints the exact SQL and executes nothing unless `--execute` is passed; "the SQL shown is byte-for-byte the SQL that runs." `repo@851886f:pnm-selfserve/selfserve_nlq/README.md#L13-L17`; `repo@851886f:pnm-selfserve/HANDOFF.md#L56-L59` ("dry-run by default").
4. **Section-level readiness tiers, owner-promoted only.** Four states — `prototype_only | stakeholder_ready | blocked | not_built` — with a hard rule that only the human owner may promote a section to `stakeholder_ready`, by deliberately editing the registry file. `repo@851886f:pnm-selfserve/selfserve_nlq/metrics_registry.py#L10-L17`. Readiness lives at the section level, not per-metric — "metrics inherit their section's readiness — no per-metric overrides." `repo@851886f:pnm-selfserve/iteration-1-metric-catalog-and-architecture.md#L279`.
5. **Unsupported-dimension refusal list.** An explicit `UNSUPPORTED_TERMS` list (city names, "weekly"/"daily", "median"/"p90"/"p99", "by vendor") causes hard refusal rather than the resolver silently answering a narrower question with the wide default number. `repo@851886f:pnm-selfserve/selfserve_nlq/metrics_registry.py#L488-L499`. This was a real bug caught in testing — "'City-wise leads in Bangalore?' wrongly resolved to `leads_overall`." `repo@851886f:pnm-selfserve/iteration-2-readiness-ledger.md#L34-L36`.
6. **Bug-for-bug fidelity, quirks disclosed, never silently fixed.** The engine deliberately replicates the source pipeline's semantics (including known population/window quirks) so answers reconcile with the existing MBR sheet; every answer footer discloses open flags. `repo@851886f:pnm-selfserve/iteration-1-metric-catalog-and-architecture.md#L315-L318`; answer-contract template at `repo@851886f:pnm-selfserve/iteration-1-metric-catalog-and-architecture.md#L345-L359`.
7. **Answer contract / trust footer** — every answer states source, month basis, "Computed: live from X (may differ from the locked MBR sheet)," readiness, and open flags verbatim. `repo@851886f:pnm-selfserve/iteration-1-metric-catalog-and-architecture.md#L345-L359`.
8. **Maker-checker / blind-checker gate before shipping a new section.** Iteration 3's build (p80/order_edits) used board review → live schema pre-flight → TDD → mirror implementation → live differential reconciliation → a blind checker pass, which is reported as PASS-WITH-NITS. `repo@851886f:pnm-selfserve/DECISION_LOG.md#L95-L103`.
9. **This mirrors — and is explicitly framed as a bridge toward — Project Argus's own confidence-gradient design** (100% governed metric store → 75-65% documented mart/fact → 55-50% staging/raw → refuse below 50%), which is the actual production system PTL is meant to graduate onto. `/Users/akshay.jain/Desktop/AI_V2/ProdOps/selfserve/project-argus-hcv-pnm-ptl-implementation-plan.md#L9`; the PnM registry is "deliberately shaped like a pre-YAML Argus metric definition... until then this stays explicitly outside the store, per the program rule that Metabase-sourced metrics without dbt models aren't eligible." `repo@851886f:pnm-selfserve/iteration-1-metric-catalog-and-architecture.md#L300-L303`.
10. **Never build the skill / never open stakeholder access without explicit owner go-ahead** — "Opening" a bundle to stakeholders and "formalizing the skill" are owner-only, produce the ledger and recommendation, nothing more.` `repo@851886f:pnm-selfserve/HANDOFF.md#L136-L137`.

## Cross-vertical metric name collisions

Instructed to distinguish rigorously: a PnM metric definition is **not** a PTL metric definition even under an identical name.

1. **`allocation %`** — **COLLISION — UNRESOLVED.**
   - PnM meaning: appears in the MBR automation (not in the Gem's exposed catalog) grouped with "deallocation %, completion %, allocation TAT p80, CAC/PAC/PoAC" as vendor-side "allocation quality" metrics — almost certainly vendor-acceptance/vendor-assignment quality, not a demand-funnel ratio. `repo@851886f:pnm-selfserve/pnm-gem-knowledge.md#L362-L368`
   - PTL meaning: `allocation % = allocation / demand` — a demand-funnel ratio, one of PTL's core derived metrics computed pan-India/city/category/week. `/Users/akshay.jain/Desktop/AI_V2/ProdOps/CLAUDE.md` (Key Derived Metrics table); `/Users/akshay.jain/Desktop/AI_V2/ProdOps/01_reference_readonly/migrated_context/prod_ops_metric_assistant_updated_master_instruction.md#L104`
   - PTL also carries *several other* allocation-named metrics in its DD that are closer to PnM's sense (vendor/partner-side): "Allocation Acceptance Rate — Batches Accepted by Owners," "Time to Allocate — P50," "% of Organic Allocation." `/Users/akshay.jain/Desktop/AI_V2/ProdOps/01_reference_readonly/migrated_context/PTL_Metrics_DD.csv` (rows ~48-50); `/Users/akshay.jain/Desktop/AI_V2/ProdOps/01_reference_readonly/migrated_context/PTL/ptl_metric_tracking_rows.csv#L44-L46`. So even *within* PTL, "allocation %" (the CLAUDE.md/master-instruction one) and "Allocation Acceptance Rate" (the DD one) are two different metrics that could be confused with each other, on top of the PnM collision.

2. **`CBDF` / `CADF` / `CAC`** — **COLLISION — UNRESOLVED (flagged as an open question in the source material itself).**
   - PTL meaning: CBDF = Cancelled Before Driver Found, CADF = Cancelled After Driver Found (explicitly defined, split at 5-min/30-min windows and overall); both are base metrics (`cbdf`, `cadf`) with `%` derived forms (`cbdf % = cbdf/demand`, `cadf % = cadf/demand`); `cac` is a third base metric (`cac % = cac/demand`) alongside them in the same demand-funnel formula family, but its expansion is not spelled out in any source read here. `/Users/akshay.jain/Desktop/AI_V2/ProdOps/01_reference_readonly/migrated_context/PTL Product Ops Review _ Akshay Hashmina and Gopika.md#L34`; `/Users/akshay.jain/Desktop/AI_V2/ProdOps/CLAUDE.md`
   - HCV meaning: the Argus implementation-plan doc lists, as one of HCV's own open semantic questions still needing resolution, "the exact definition of `CBDF + CADF − CAC`" — i.e. HCV uses the identical three-acronym family and has *not yet settled* what they mean or how they combine. `/Users/akshay.jain/Desktop/AI_V2/ProdOps/selfserve/project-argus-hcv-pnm-ptl-implementation-plan.md#L103`
   - Net: two verticals share the exact same three-letter acronyms in the same demand/cancellation domain, and neither this extract nor the cited HCV source resolves whether they mean the same thing.

3. **`CAC` (separately, PnM's usage)** — **COLLISION — UNRESOLVED.** PnM's automation lists "CAC/PAC/PoAC" together as allocation-stage acronyms (grouped with allocation %/deallocation %/completion %), which reads as vendor-allocation-lifecycle codes, not a demand-side cancellation metric and not "Customer Acquisition Cost." `repo@851886f:pnm-selfserve/pnm-gem-knowledge.md#L365`. This is a third, mutually-inconsistent sense of `CAC` alongside PTL's (demand-funnel) and the conventional CPG/marketing sense (Customer Acquisition Cost) — none of the three is confirmed as *the* meaning without an owner ruling.

4. **`conversion`** — **COLLISION — likely different grain, not verified same.**
   - PnM meaning: `conversion_overall = orders_overall ÷ leads_overall` (and per-channel variants), a precisely defined *period* (not cohort) monthly ratio with an explicit Nano-asymmetry caveat (non-Nano orders ÷ Nano-inclusive leads). `repo@851886f:pnm-selfserve/pnm-gem-knowledge.md#L230, L238-L240`
   - PTL meaning: PTL's DD has "PTL Activation Rate — Business Users (First Order within 7 Days of Card View)" under an "Activation & Conversion" domain, and "Quote-to-Book" conversion (quote generated → order booked) discussed in the product-ops review — a funnel-stage or time-boxed activation ratio, structurally different from PnM's same-month lead-to-order ratio. `/Users/akshay.jain/Desktop/AI_V2/ProdOps/01_reference_readonly/migrated_context/PTL_Metrics_DD.csv#L9`; `/Users/akshay.jain/Desktop/AI_V2/ProdOps/01_reference_readonly/migrated_context/PTL Product Ops Review _ Akshay Hashmina and Gopika.md#L101`
   - Not the same field name in either catalog ("conversion_overall" vs "Activation Rate"/"Quote-to-Book"), so this is a soft/conceptual collision on the word "conversion," not an identical-metric-id collision — flagged for completeness, lower severity than #1-#3.

5. **`NPS`** — present in both PTL (Dec 4.40, Jan 4.45, per historical MBR evidence) and referenced generically across Porter verticals as a support/experience signal; not deep-dived here since neither source gives PnM an NPS *formula* to compare against (PnM's exposed catalog doesn't surface NPS as a queryable metric — it's mentioned only as an out-of-catalog automation output). ## Porter metric conventions

Stated house rules found in these sources (both PTL-sourced and PnM-sourced), useful because they recur nearly verbatim across verticals:

- **Aggregate-then-ratio, never average pre-computed ratios.** PTL master instruction, framed as "non-negotiable": "always aggregate numerator and denominator first at the required cut... do not compute ratios at daily level and then average them... do not take simple averages of pre-computed percentages." `/Users/akshay.jain/Desktop/AI_V2/ProdOps/01_reference_readonly/migrated_context/prod_ops_metric_assistant_updated_master_instruction.md#L136-L143`. PnM's independent NL-layer design states the identical rule for its own derived metrics: "ratios from raw counts (never averaged)...
