## FINDING 1 — `orders.state` enum CONFIRMED (resolves standing assumption P1)

Verbatim from the card's native SQL:

```sql
CASE
    WHEN ORDERS.state = 0 THEN 'Open'
    WHEN ORDERS.state = 1 THEN 'Assigned'
    WHEN ORDERS.state = 2 THEN 'Picked_up'
    WHEN ORDERS.state = 3 THEN 'Completed'
    WHEN ORDERS.state = 4 THEN 'Cancelled'
END AS order_status
```

- **Resolves:** `STATE_ENUM_CONFIRMED = False` in `selfserve_nlq/core.py`, and the standing
  "state enum (3=completed, 4=cancelled) UNCONFIRMED (P1)" flag carried in every prior artifact.
- **Confidence: verified** — rank-1 evidence under the D-009 precedence ladder (observed card SQL),
  from a heavily-used production card (93,521 views, last used 2026-07-29).
- **Residual caveat:** this is a human-authored CASE mapping in a card, NOT a warehouse data
  dictionary or an enum constraint. It is the strongest available evidence; it is not a schema
  guarantee. A data-dictionary confirmation would upgrade it from "verified via card SQL" to
  "verified via source of truth". → keep one GAPS row open for that upgrade.
- **Bonus:** states 0/1/2 (`Open`/`Assigned`/`Picked_up`) were undocumented in every prior artifact.

## FINDING 5 — timezone handling (closes P2c's "no corroboration" gap)
Two distinct patterns, both present:
- **Display/derivation:** `CONVERT_TIMEZONE('UTC', 'Asia/Kolkata', TO_TIMESTAMP(col))`
- **Pruning-safe filter:** `ORDERS.pickup_slot_start >= DATEADD('minute', -330, DATEADD('day', -1, CURRENT_DATE)::timestamp_ntz)::timestamp_ltz`
  — carries the inline comment `-- KEY FIX: UTC range enables micro-partition pruning`.
- Confirms both the workspace CLAUDE.md convention and the prototype's `DATEADD(-330)` approach.
  P2c reported finding no corroboration for the UTC+330 rule; this is primary corroboration.
- **Counter-example in the same card** (optional filter, not the main predicate):
  `[[AND DATE(ORDERS.pickup_slot_start + INTERVAL '330 minutes') = {{pickup_date}}]]` — wraps the
  timestamp column in an expression, the exact anti-pattern the "KEY FIX" comment warns against.
  → note as an observed inconsistency, not a KB rule.

## FINDING 7 — repeated / duplicate order definition
`is_repeated_order` = same `customer_mobile`, same IST pickup date, both orders `state != 4`,
and **both** pickup AND drop within `HAVERSINE(...) < 0.1` (≈100 m) of each other. Bounded to
`CURRENT_DATE -1 .. +2`. Emits `dup_count`, `repeated_sibling_order_ids`, `is_first_duplicate`,
`original_order_id`. **verified.**
- NOTE: this is an *operational duplicate-booking* flag. It is NOT the same concept as the
  "repeat user share" / "M1 retention" metrics in the Notion review. Name-collision risk. → GAPS row.
